### Разработанная грамматика
```
1) <START> -> 'struct' <SPACE>
2) <SPACE> -> ' ' <NAME_STRUCT>
3) <NAME_STRUCT> -> letter <NAME_STRUCT_REM>
4) <NAME_STRUCT_REM> -> letter <NAME_STRUCT_REM> | digit <NAME_STRUCT_REM> | '_' <NAME_STRUCT_REM> | '{' <BODY>
5) <BODY> -> letter <ID>
6) <ID> -> letter <ID> | digit <ID> | '_' <ID> | ':' <TYPE>
7) <TYPE> -> 'String' <END_FIELD> | 'u64' <END_FIELD> | 'char' <END_FIELD> | 'f64' <END_FIELD> | 'bool' <END_FIELD>
8) <END_FIELD> -> ',' <BODY> | '}' <END_BODY>
9) <END_BODY> -> ';'
```

Следуя введенному формальному определению грамматики, представим G[‹START›] ее составляющими:

```
Z = ‹START ›;
VT = { a, b, c, ..., z, A, B, C, ..., Z, 0, 1, 2, ..., 9, _, {, }, :, ,, ;, _};
VN = {<START>, <SPACE>, <NAME_STRUCT>, <NAME_STRUCT_REM>, <BODY>, <ID>, <TYPE>, <END_FIELD>, <END_BODY>}.
```

Согласно классификации Хомского, грамматика G[‹START›] является автоматной.
Правила (1)-(9) относятся к классу праворекурсивных продукций (A → aB | a | ε)

## Метод Айронса для автоматной грамматики

Разрабатываемый синтаксический анализатор построен на базе автоматной грамматики. Реализация алгоритма Айронса для автоматной грамматики имеет следующую особенность.
Дерево разбора с использованием автоматной грамматики представлено на рисунке.

![Айронс](screenshots/airs1.png)

Таким образом, при возникновении синтаксической ошибки в процессе разбора с использованием автоматной грамматики, в дереве разбора всегда будет только один недостроенный куст.

![Айронс](screenshots/airs2.png)

Поскольку единственный недостроенный куст – это тот, во время построения которого возникла синтаксическая ошибка, то это единственный куст, к которому можно привязать оставшуюся входную цепочку символов.
Алгоритм нейтрализации был сведен к последовательному удалению следующего символа во входной цепочке до тех пор, пока следующий символ не окажется одним из допустимых в данный момент разбора.

## Индивидуальное задание: передача структур

### Исходный код (`struct_pass.c`)

См. `examples/lab7/struct_pass.c`.

### 1. AST и IR

Команды аналогичны общей части; в GUI — **F5** на открытом `struct_pass.c`.

### 2. Передача при -O0 и -O2

**-O0:** в IR обычно видны:

- тип `%struct.Point`, размещение на стеке через `alloca`;
- параметр функции `sum` — часто `%"struct.Point"*` с атрибутом **`byval`** (семантика передачи **по значению** на уровне ABI: копия для вызываемой функции);
- обращения к полям через `getelementptr`, `load`, `store`;
- вызов `call @sum(...)`.

**-O2** (аргументы `{2, 3}` известны на этапе компиляции):

- вызов `@sum` **исчезает** (inlining + constant folding);
- в `main` остаётся, как правило, прямой вывод `5` через `printf`;
- отдельная передача структуры как аргумента **не нужна** — оптимизатор устранил её.

**Ответ на вопрос «по значению / по ссылке?»:** в исходном C — **по значению**. В LLVM при -O0 это отражается как **`byval`** или копирование через стек; это **не** передача «по ссылке» в смысле C++ reference, хотя в IR используется указатель на копию. При -O2 для данного примера передача **исчезает** из-за оптимизаций.

### 3. CFG для `sum` и `main`

При **-O0** — два CFG: `.sum.dot` и `.main.dot`.  
При **-O2** — CFG для `sum` может **не создаться**, если функция удалена/встроена.

### 4. `__attribute__((always_inline))`

Файл: `examples/lab7/struct_pass_inline.c`.

```bash
clang -O2 -S -emit-llvm -std=c11 examples/lab7/struct_pass_inline.c -o inline_O2.ll
```

Атрибут `alwaysinline` заставляет компилятор **встраивать** `sum` даже при агрессивных эвристиках. Для константного `p = {2,3}` результат сопоставим с обычным `-O2`: вызов исчезает, остаётся упрощённый `main`.

### 5. Вывод по индивидуальному заданию

LLVM не меняет семантику C «по значению» на «по ссылке», а представляет копирование через **byval** / стек / регистры (ABI). Оптимизации **-O2** (`inline`, `constprop`, `mem2reg`, `SROA`, `DCE`) могут:

- разложить структуру на скаляры в регистрах;
- встроить маленькую функцию и убрать вызов;
- полностью убрать передачу struct, если аргументы известны как константы.

## Выводы: контрольные вопросы

1. **Clang** — фронтенд компилятора (парсинг, AST, семантика, генерация IR); часто используется как библиотека для анализа и IDE.  
2. **LLVM** — набор библиотек и IR для оптимизации и генерации кода; backend-ы для разных платформ.  
3. **AST** отражает синтаксическую структуру исходника; **IR** — низкоуровневые инструкции, SSA, близко к машине.  
4. **IR** нужен для переносимых оптимизаций и единого pipeline независимо от языка.  
5. **`alloca`** выделяет память на стеке в IR; до **mem2reg** переменные часто живут в памяти.  
6. **Оптимизация** ускоряет код, уменьшает размер, убирает лишние операции при сохранении семантики.  
7. **SSA** — каждое значение присваивается один раз; упрощает анализ потоков данных и оптимизации.  
8. **CFG** — граф базовых блоков и переходов; нужен для анализа путей, циклов, оптимизаций.  
9. Арифметика в IR: типизированные инструкции `add`, `mul`, `fadd` и т.д. для целых/вещественных.  
10. Функции — естиницы с отдельным CFG, своим набором оптимизаций и ABI.  
11. Короткая функция с одним вызовом часто **встраивается** (`inline`) и может быть удалена.  
12. IR и CFG дают формальную структуру для автоматических преобразований; исходный текст C сложнее и неоднозначнее для таких проходов.
